The operator-error lens names hand edits, but this one ignores both the read-mostly instruction and the column's type, so it is not a reachable defect under the rubric. The landing ran as a loop over a tier-ordered queue, one `land.sh` at a time, with a keeper that
restarted it after a wait timeout and stopped it for a human on anything else. Three things about the
squash queue that pass 2 did not meet:

- **A batch of PRs is a CI storm, and the storm outlives the PRs.** Twenty-one fix branches pushed within
  an hour queued about 90 workflow runs behind the organisation's runner cap. The first PR's last summary
  check was still queued when `land.sh`'s fixed 60-minute wait expired, and the loop read the timeout as
  a failure. Every one of those runs was for a head the loop was about to rebase away. The PR workflows
  need a `concurrency` group that cancels a superseded head's runs, and the wait caps need to be
  configurable and retryable. Cancelling the queued runs by hand was denied to the coordinator's tooling
  as interference with workloads, so the storm drained on its own in about 90 minutes.
- **The image cache never reached `main`.** #562's cache of the TimescaleDB fleet image is readable from
  the ref that saved it and from `main`. Twenty-three PR refs saved their own copy (303 MB each, 7.65 GB
  of the 10 GB cap); `main` never did, because both of its post-#562 push runs missed the cache and were
  then refused by the same quota. So every merge group pulled from ECR, and #606's fell out on the data

- **`wait_merge` can read a merge as a fall-out.** #609's queue entry read `OPEN none` for the seconds
