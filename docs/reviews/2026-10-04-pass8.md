## Fell in verification

- F12-04: The reproduction does reproduce on both trees (the classifier run again: prefix, endpoint and fetch_rows go back to their defaults on the second call), but the code and the documentation do not disagree. The README sentence (pgpm_archive/README.md:31-33) belongs to the first-call quick start: it comes right after `select archive.configure('public.events', 'my-archive-bucket');   -- region/endpoint/prefix/etc. all default sanely`. It says the other parameters `all have sensible defaults -- pass only what you need to override`, and 'override' there means overriding those defaults. Read literally, it says an omitted parameter takes its default, and that is exactly what happens on every call, the second one included. Nothing in the README, docs/reference.md, guide.md or runbook.md says that a later call keeps stored values (archive.configure is not documented anywhere else). The function's own comment calls it 'an upsert with every connection-setting column as a named, defaulted parameter', and tests/archive/db/09_configure_test.sql pins the replace-the-row behaviour on purpose ('the upsert overwrites the bucket/region/compress'). So the claim rests on an operator reading the sentence as promising that omitted settings are kept, which it does not say. A missing note about what a second call does is a gap, not a document that is wrong (the Tier 4 rubric needs it to be wrong) and not a broken documented contract (Tier 3). No open issue covers it (open.json has no configure-reset bullet), and no rebuilt reproduction was needed.
- F5-04: Reproduces on both trees (classifier re-run: tests 3 and 5 fail, have 300000 want 2000, liveness 1/2/4 pass), but the rubric names no consequence. No document promises that pgpm preserves pgsql-http session options: docs/reference.md, guide.md, runbook.md and README.md never mention CURLOPT, http_set_curlopt or the caller's http settings, and archive.s3_signed_request's own comment (install.sql:225-227) promises only canonical query handling. The function-SET-clause restorations the claim contrasts (install.sql:2608, 'the SET clause restores the caller's setting on return') are code comments about specific GUCs pinned for byte-exactness (#551, #781), not a published contract covering extension state. pgsql-http documents http_set_curlopt as session-scoped state any code in the session may change, and pgpm's own requests correctly override whatever the caller set. The effect is only that the caller's later, unrelated http() calls get a longer (5 min) ceiling than they chose: no data loss or wrong result (not T1), nothing of pgpm's wedges or stops making progress (not T2; pg_cron ticks run in their own connection, so a tick leaks into no other work), pgpm neither acts where it should refuse nor breaks a documented contract (not T3), and no doc or test is wrong (not T4/T5). Not an open issue: open.json mentions pgsql-http only for the PG 18 Dockerfile build. Undocumented and harmless by the rubric.
